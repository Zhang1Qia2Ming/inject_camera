# RAW12 10Hz 源按 30Hz 输出设计

## 目标

保持三路 PCIe/MIPI 物理输出均为 30Hz，同时恢复原 MCAP 的内容时间轴：

- lane0 / 前远：10Hz 源，每个 RAW12 帧连续发送 3 次。
- lane1 / 前广：30Hz 源，每个 RAW12 帧发送 1 次。
- lane2 / 后视：10Hz 源，每个 RAW12 帧连续发送 3 次。

## 方案选择

采用发送时重复读取内存中同一帧的方案。它不扩充约 25GB 的 RAW 文件，不修改
MCAP 转换结果，也不增加 FPGA、DDR、MIPI 或域控逻辑。

未采用的方案：

- 离线生成三倍帧数文件：会额外占用约 10GB，且重复信息没有必要落盘。
- 降低 lane0/lane2 的物理发送率到 10Hz：不满足域控期望的 30fps 输入。

## 发送行为

发送线程保持统一的 `33.333333ms` 节拍。每次完整 `write()` 仍然发送
`12,441,600` 字节并产生一个帧边界。

发送成功后更新重复计数：

1. 重复次数未达到该 lane 的倍率时，cursor 保持不变。
2. 达到倍率后，cursor 前进一帧。
3. 到达已加载数据末尾后回到首帧。

日志中的 `lane N frames` 仍表示物理发送帧数。新增启动信息明确显示每路源频率、
输出频率和重复倍率，避免把 30°/120°视场角误认为帧率。

## 同步边界

本修改只修复内容播放速度，不声称实现硬件帧同步。三个发送线程仍可能存在微小相位
差，注入卡与真实相机也没有共同 FSYNC。复测后：

- 若 `nvsipl_camera` 原始采集连续、仅网页 H.265 马赛克，检查共享编码/发布链路。
- 若原始采集出现 drop、discontinuity 或 timeout，再设计统一线程 epoch 或硬件 FSYNC。

## 测试

增加纯函数测试，验证：

- 倍率3产生 `0,0,0,1,1,1,2...` 的源帧序列。
- 倍率1产生 `0,1,2...`。
- 最后一帧完成重复后正确回到首帧。

编译时启用 `-Wall -Wextra -Werror`，并运行现有节拍测试及主机侧Python回归。
